# Тест-план приложения «В Хосписе»

## 1. Описание ПО

«В Хосписе» — учебное Android-приложение для просмотра новостей и работы с ними. Пользователь может авторизоваться, открыть главную страницу, читать новости, применять сортировку и фильтры, перейти в раздел «Наша миссия». Администратор дополнительно может создавать, редактировать, изменять статус и удалять новости.

Пакет приложения: `ru.edu.qamid`. Проверяемая версия: 1.0.0 (14). Учётные данные из задания: `login2 / password2`.

## 2. Цель

Проверить основные функции приложения вручную, оформить результаты в чек-листе и тест-кейсах, а затем подготовить понятный план выборочной автоматизации наиболее важных и повторяемых сценариев.

## 3. Что надо тестировать

| Раздел | Что проверяется |
| --- | --- |
| Авторизация | Вход, пустые поля, неверные данные, выход, повторный вход |
| Главная страница | Отображение новостей, сворачивание блока, переходы |
| Новости | Открытие карточки, сортировка, обновление, фильтры |
| Управление новостями | Создание, редактирование, статус, удаление, фильтры |
| Наша миссия | Открытие раздела, цитаты, раскрытие карточек, переходы |
| Интерфейс и устойчивость | Поворот, увеличенный шрифт, длинный текст, работа после отсутствия сети и возврата из фона |

Не входят в объём: нагрузочное тестирование, проверка безопасности, iOS, регистрация, восстановление пароля и функции, которых нет в текущей версии приложения.

## 4. Что будут тестировать

Ручная часть охватывает все перечисленные разделы. Для автоматизации выбираются только важные, стабильные и часто повторяемые сценарии. Полный список ручных проверок находится в `Check.xlsx`, подробные шаги и результаты — в `Cases.xlsx`.

### Сортировка тест-кейсов по степени автоматизации

| Группа | Сценарии | Причина выбора |
| --- | --- | --- |
| Автоматизировано | Успешная авторизация; пустые поля; неверный пароль; открытие формы новости; обязательные поля новости; создание новости; открытие «Нашей миссии»; раскрытие цитаты | Эти сценарии важны, повторяемы и имеют понятный ожидаемый результат. |
| Планируется автоматизировать | Редактирование; удаление своей новости; сортировка | Эти сценарии важны, но для безопасного прогона на общем стенде нужно подготовить и затем удалить собственные данные. |
| Проверять вручную | Увеличенный системный шрифт; поворот экрана; удобство длинного текста с клавиатурой; возврат из фона; внешний вид экранов | Нужна визуальная оценка и работа с настройками устройства. Результат зависит от размера экрана и поведения системы. |
| Проверять вручную или после подготовки данных | Фильтры по точным границам дат; период в один день; сочетание категории и периода; статус новости в общем списке | Нужны контролируемые новости с определёнными датами, временем и статусами. На общем учебном сервере эти данные могут меняться. |
| Не автоматизировать на текущем этапе | Проверка роли обычного пользователя | В задании нет учётной записи пользователя без прав администратора. |

## 5. Как будут тестировать

### Ручное тестирование

Проверки выполняются по `Cases.xlsx` на эмуляторе Android API 36. Результат каждой проверки отмечается как «Пройден», «Не пройден», «Заблокирован» или «Не выполнен». Для ошибок сохраняются скриншоты и описание фактического результата.

### Автоматизация

Автоматизация выполняется на JavaScript. Используются Node.js, Appium, WebdriverIO, Android SDK и Allure.

Тесты разделены по функциям: авторизация, новости и «Наша миссия». Взаимодействие с экраном вынесено в Page Objects и Steps. В тестах нет фиксированных `sleep()`; вместо них используются ожидания нужного элемента или состояния. Каждый тест очищает данные приложения перед запуском и не зависит от порядка запуска.

Перед написанием тестов можно использовать Espresso Test Recorder как вспомогательный инструмент: записать простой сценарий, изучить элементы экрана и затем перенести сценарий в выбранную структуру автотестов с Page Objects.

## 6. Техники тест-дизайна и обоснование

| Техника | Где применяется | Почему подходит |
| --- | --- | --- |
| Классы эквивалентности | Логин и пароль: корректные, пустые, из пробелов, неверные | Позволяет проверить разные типы ввода без перебора всех вариантов. |
| Граничные значения | Время публикации 00:00 и 23:59; начало и конец периода | Ошибки часто возникают на границах диапазона. |
| Таблица решений | Фильтр статусов: активна, неактивна, оба статуса, ни один статус | Результат зависит от сочетания двух переключателей. |
| Переходы состояний | Вход/выход; активная/неактивная новость; сохранение/отмена/удаление | Помогает проверить, как приложение меняет состояние после действия пользователя. |
| Исследовательское тестирование | Поворот, клавиатура, увеличенный шрифт, возврат из фона | Поведение зависит от устройства и не всегда описано в требованиях. |

## 7. Когда будут тестировать

1. Подготовка среды и проверка запуска приложения.
2. Smoke-проверка: вход, открытие новостей, переход к панели администратора.
3. Ручной прогон тест-кейсов по функциональным разделам.
4. Фиксация результатов и ошибок в тестовой документации.
5. После проверки первого этапа — реализация и запуск выбранных автотестов.
6. Сравнение ручных и автоматизированных проверок, оформление итогового отчёта.

## 8. Критерии начала тестирования

- приложение установлено и запускается;
- доступен эмулятор Android API 36;
- есть подключение к учебному серверу;
- доступны учётные данные `login2 / password2`;
- подготовлены `Check.xlsx` и `Cases.xlsx`;
- для сценариев с созданием новости определены уникальные тестовые заголовки.

## 9. Критерии окончания тестирования

- выполнены все сценарии, для которых есть необходимые данные и условия;
- у каждого тест-кейса указан статус и фактический результат;
- для каждой найденной ошибки есть шаги, ожидаемый и фактический результат, а также доказательство;
- собственные тестовые новости удалены;
- тестовая документация проверена и готова к отправке;
- для второго этапа: выбраны автотесты, получен результат их запуска и сформирован Allure-отчёт.

## 12. Интервальная оценка с учётом рисков

Оценка дана интервалом, потому что часть времени зависит от учебного сервера, тестовых данных и поведения эмулятора.

| Работа | Оптимистичная оценка | Реалистичная оценка | При рисках |
| --- | ---: | ---: | ---: |
| Подготовка среды и smoke-проверка | 1 час | 2 часа | 4 часа |
| Ручной прогон и фиксация результатов | 4 часа | 7 часов | 12 часов |
| Исправление тестовой документации | 2 часа | 4 часа | 7 часов |
| Подготовка выбранных автотестов | 8 часов | 14 часов | 24 часа |
| Отчёт Allure и итоговая документация | 2 часа | 4 часа | 8 часов |

Реалистичная оценка всего проекта: 31 час. При проблемах с окружением, сервером или тестовыми данными: до 55 часов.

## 13. Риски и пути их разрешения

| Риск | Вероятность | Влияние | Как уменьшить риск |
| --- | --- | --- | --- |
| Общий учебный сервер меняется из-за действий других студентов | Средняя | Высокое | Использовать уникальные заголовки тестовых новостей, проверять результат сразу, не менять чужие данные. |
| Нет тестовых данных на нужные даты и время | Высокая | Среднее | Использовать подготовленные фикстуры, если они появятся; иначе честно фиксировать ограничение. |
| Нет учётной записи обычного пользователя | Высокая | Среднее | Запросить учётную запись у преподавателя или отметить сценарий как заблокированный. |
| Эмулятор не запускается или работает нестабильно | Средняя | Среднее | Перезапустить эмулятор, проверить Android SDK и ADB, сохранить настройки среды. |
| Элементы интерфейса меняются или загружаются медленно | Средняя | Высокое | В автотестах использовать resource-id и явные ожидания, не использовать `sleep()`. |
| Автотесты создают новости и мешают друг другу | Средняя | Высокое | Создавать уникальные данные в каждом тесте и очищать их после завершения. |
| Негативный тест выглядит как падение автотеста | Средняя | Среднее | В тесте явно проверить ожидаемое сообщение об ошибке и описать ожидаемый негативный результат. |
| Allure-отчёт не формируется | Низкая | Среднее | Проверить настройку репортера на простом тесте до написания всего набора. |

## 16. Результаты ручного тестирования на текущий момент

Ручная часть выполнена на Android API 36. В `Cases.xlsx` указаны результаты: 59 сценариев пройдены, 2 не пройдены, 1 заблокирован, 7 не выполнены из-за конкретных ограничений тестовых данных или отдельного прогона. Найдена ошибка BUG-001: при неверных учётных данных отображается общее сообщение вместо сообщения «Неверный логин или пароль».
